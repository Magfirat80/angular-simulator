Задача №1: Будет создан 1 экземпляр CounterService (он является Singleton).Почему?
  providedIn: 'root':
Эта декорация говорит Angular зарегистрировать сервис в корневом внедрителе зависимости (Root Injector). Корневой инжектор создается один раз при старте приложения и хранит единственную копию сервиса на весь жизненный цикл приложения.
  inject(CounterService):
Оба компонента (ComponentA и ComponentB) запрашивают сервис у DI-контейнера Angular. Так как ни ComponentA, ни ComponentB, ни их родительские модули/компоненты не объявляют CounterService в своем локальном массиве providers: [...], Angular поднимается по дереву инжекторов до самого верха — до Root Injector — и возвращает им одну и ту же ссылку на уже созданный экземпляр.
  В результате значение counter.id у ComponentA и ComponentB будет абсолютно одинаковым.


Задача №2: Будет создано 2 экземпляра CounterService. Почему?
  Иерархия инжекторов и переопределение:
Хотя у сервиса указан @Injectable({ providedIn: 'root' }), явное указание providers: [CounterService] в декораторе @Component создаёт локальный провайдер на уровне инжектора данного элемента (ElementInjector). Это переопределяет корневой провайдер для компонента и его дочерних элементов.
  Изоляция компонентов:
Каждый создаваемый в DOM экземпляр компонента <app-child> создает свой собственный экземпляр ElementInjector.
  Подсчёт:
Первый <app-child> создаёт свой локальный CounterService (1-й экземпляр).
Второй <app-child> создаёт свой собственный отдельный CounterService (2-й экземпляр).
Корневой экземпляр (root) даже не будет создан, так как поиск зависимости останавливается на уровне элемента и не доходит до Root Injector.
  В результате у каждого из двух компонентов counter.id будет разным.


Задача №3: ChildComponent получит экземпляр LoggerService, созданный в ParentComponent (из его ElementInjector), а не корневой (root). Почему?
  Механизм разрешения зависимостей (DI Resolution Rules):
Когда ChildComponent запрашивает LoggerService через inject(LoggerService), Angular начинает поиск зависимости снизу вверх по дереву инжекторов:
Шаг 1: Проверяет локальный инжектор самого ChildComponent. Там провайдер не объявление.
Шаг 2: Поднимается к родительскому компоненту (ParentComponent).
Шаг 3: В ParentComponent указан providers: [LoggerService]. Angular находит этот провайдер, берет экземпляр, привязанный к ParentComponent, и возвращает его в ChildComponent.
  Остановка поиска:
Поскольку Angular находит совпадение на уровне ParentComponent, он останавливает поиск и не поднимается выше до Root Injector.


Задача №4: Существует 1 экземпляр LoggerService. Почему?
  Суть useExisting (Алиас):
Токен { provide: 'LOGGER', useExisting: LoggerService } не создает новый экземпляр класса. Он говорит Angular DI-контейнеру: «Когда кто-то запрашивает токен 'LOGGER', не нужно создавать новый объект — просто верни ссылку на уже существующий экземпляр, зарегистрированный под токеном LoggerService».
  Как это работает при внедрении:
При inject(LoggerService) (переменная a) Angular возвращает экземпляр LoggerService.
При inject('LOGGER') (переменная b) Angular по правилу useExisting перенаправляет запрос к LoggerService и возвращает тот же самый экземпляр.
  В результате a === b вернет true — обе переменные ссылаются на один и тот же объект в памяти.


Задача №5: useFactory будет вызвана при первом inject(). Почему?
  Ленивая инициализация (Lazy Initialization):
В Angular контейнер внедрения зависимостей (DI) работает по требованию. Он не инстанциирует сервисы заранее при запуске приложения просто потому, что они объявлены в массиве providers.
  Кэширование результатов (Singleton по умолчанию):
При первом вызове inject(LoggerService) (или запросе зависимости через конструктор) Angular видит провайдер, выполняет функцию useFactory и кэширует переданный ею результат в соответствующем инжекторе.
  Последующие вызовы:
При всех последующих вызовах inject(LoggerService) в пределах зоны видимости этого инжектора Angular берет уже готовый, ранее закэшированный экземпляр и не вызывает useFactory повторно.


Задача №6: В value окажется массив строк: ['A', 'B']. Почему?
  Флаг multi: true:
Указывая multi: true, вы сообщаете Angular DI-контейнеру, что данный токен внедрения зависимостей может принимать множество значений, и их нужно объединить в один массив, а не перезаписывать предыдущее значение последующим.
  Формирование результата:
Каждый провайдер с этим токеном добавляет свой результат (useValue: 'A' и useValue: 'B') в единую коллекцию. Порядок элементов в массиве точно соответствует порядку объявления провайдеров в массиве providers.


Задача №7: переменную logger запишется null (ошибки не будет). Почему?
  Флаг optional: true:
По умолчанию, если Angular DI не находит провайдер для запрашиваемого сервиса, он выбрасывает фатальную ошибку NullInjectorError: No provider for LoggerService!. Опция { optional: true } (или аналог — декоратор @Optional()) меняет это поведение и сообщает контейнеру: «Если зависимость не найдена в дереве инжекторов, не выбрасывай ошибку, а просто верни null».
  Работа inject():
Так как LoggerService нигде не зарегистрирован в массиве providers и не имеет декоратора @Injectable({ providedIn: 'root' }), Angular корректно обрабатывает отсутствие провайдера и присваивает значение null.


Задача №8: Произойдет ошибка во время выполнения (Runtime Error): NullInjectorError: No provider for LoggerService!. Почему?
  Флаг self: true:
Опция { self: true } (аналог декоратора @Self()) жестко ограничивает поиск зависимости только локальным инжектором текущего компонента (ElementInjector). Она запрещает Angular искать сервис выше по дереву компонентов или обращаться к корневому инжектору (Root Injector).
  Игнорирование providedIn: 'root':
Хотя у LoggerService есть декоратор @Injectable({ providedIn: 'root' }), позволяющий регистрировать его глобально, флаг { self: true } заставляет Angular полностью проигнорировать Root Injector.
  Результат поиска:
Так как в собственном массиве providers компонента ChildComponent данный сервис не объявлен, а подниматься выше Angular запрещено, DI-контейнер завершает поиск неудачей и выбрасывает ошибку.
(Чтобы код работал без ошибки при отсутствии локального провайдера, можно было бы добавить флаг optional: true — тогда в logger вернулся бы null).


Задача №9: ChildComponent получит экземпляр LoggerService, созданный в ParentComponent. Почему?
  Флаг skipSelf: true:
Опция { skipSelf: true } (аналог декоратора @SkipSelf()) заставляет Angular DI-контейнер пропустить локальный инжектор самого ChildComponent и начать поиск зависимости сразу с инжектора родительского элемента.
  Поиск по дереву инжекторов:
Angular игнорирует локальный уровень ChildComponent и поднимается к ParentComponent.
В ParentComponent объявлен providers: [LoggerService], поэтому Angular берет и возвращает экземпляр, созданный на уровне родительского компонента.
(Если бы у ParentComponent не было объявлено providers: [LoggerService], Angular продолжить бы поиск выше по дереву инжекторов и в итоге вернул бы глобальный root-экземпляр).


Задача №10: Произойдет ошибка во время выполнения (Runtime Error): NullInjectorError: No provider for ApiService!. Почему?
  Отсутствие декоратора или объявления в providers:
Если класс ApiService не имеет декоратора @Injectable({ providedIn: 'root' }) и при этом нигде не добавлен в массив providers (ни в компоненте, ни в директиве, ни в NgModule), Angular DI-контейнер не знает, как его создавать.
  Стандартное поведение DI:
Когда вызывается inject(ApiService), Angular проходит по всему дереву инжекторов от текущего элемента до самого верха (Root Injector и NullInjector). Не найдя ни одного провайдера для этого токена, NullInjector выбрасывает исключение и приложение аварийно завершает работу.


Задача №11: Будет создан 1 экземпляр LoggerService. Почему?
  Singleton в корневом инжекторе:
Декоратор @Injectable({ providedIn: 'root' }) регистрирует LoggerService в единственном числе на уровне Root Injector.
  Кэширование экземпляров:
Когда внутри UserService выполняется инициализация свойства logger1 = inject(LoggerService), Angular DI создаёт первый и единственный экземпляр LoggerService и сохраняет ссылку на него в своём внутреннем реестре.
  Повторный запрос:
Когда следом инициализируется logger2 = inject(LoggerService), Angular берет из реестра уже созданный кэшированный экземпляр и присваивает его переменной logger2.
В результате logger1 === logger2 вернет true (обе переменные ссылаются на один и тот же объект в памяти).


Задача №12: Ответы на вопросы по структуре приложения:
  1. Сколько экземпляров LoggerService существует?
Существует 2 экземпляра LoggerService:Глобальный (Root) — автоматически созданный на уровне Root Injector благодаря @Injectable({ providedIn: 'root' }).Локальный (Header) — созданный в ElementInjector компонента HeaderComponent из-за явного указания providers: [LoggerService].
  2. Какой экземпляр получит HeaderComponent?
HeaderComponent получит свой локальный экземпляр, так как он объявлен в его собственном массиве providers. Это переопределяет корневой провайдер для данного компонента и его возможных детей.
  3. Какой экземпляр получит DashboardComponent?
DashboardComponent получит глобальный экземпляр (Root).В DashboardComponent нет локального провайдера, и он не является дочерним элементом для HeaderComponent (они параллельные ветви одного уровня), поэтому поиск поднимается напрямую к Root Injector.
  4. Какой экземпляр получит UserCardComponent?
UserCardComponent получит глобальный экземпляр (Root).Он находится внутри DashboardComponent, у которого нет своего провайдера, и никак не связан с изолированным инжектором HeaderComponent.
  5. По какой цепочке Injector'ов Angular будет искать зависимость в UserCardComponent?
Цепочка поиска (снизу вверх):$$\text{UserCardComponent (ElementInjector)} \longrightarrow \text{DashboardComponent (ElementInjector)} \longrightarrow \text{AppComponent (ElementInjector)} \longrightarrow \text{Root Injector (EnvironmentInjector)}$$UserCardInjector: проверяет себя — провайдера нет.DashboardInjector: поднимается к родителю — провайдера нет.AppInjector: поднимается к корню компонентов — провайдера нет.Root Injector: находит декоратор providedIn: 'root', берет глобальный экземпляр и возвращает его. Поиск успешно завершен.


Задача №13: После вызова inject(A) Angular выполнит процесс разрешения зависимостей по определенному алгоритму. Пошаговая цепочка выполнения состоит из следующих этапов:
  Шаг 1. Обращение к inject(A) и проверка кэша
Angular обращается к текущему активному инжектору (в данном случае к Root Injector / EnvironmentInjector).
Инжектор проверяет свой внутренний реестр экземпляров (кэш/Map по ключу-току A).
Экземпляр класса A еще не создан. Инжектор находит соответствующую запись о провайдере A (providedIn: 'root') и переходит к созданию объекта.
  Шаг 2. Разрешение цепочки зависимостей (Рекурсивный стек)
Чтобы создать объект A, Angular начинает исполнять его конструктор/инициализаторы полей в текущем контексте внедрения:
Создание A:
Инициализируется поле b = inject(B).
Вызов inject(B) приостанавливает создание A и запрашивает сервис B у Root Injector.
Экземпляр B отсутствует в кэше.
Переход к B:
Начинается создание экземпляра B.
Инициализируется поле c = inject(C).
Вызов inject(C) приостанавливает создание B и запрашивает сервис C.
Экземпляр C отсутствует в кэше.
Переход к C:
Начинается создание экземпляра C.
Инициализируется поле d = inject(D).
Вызов inject(D) приостанавливает создание C и запрашивает сервис D.
Экземпляр D отсутствует в кэше.
Переход к D:
Начинается создание экземпляра D.
Инициализируется поле logger = inject(LoggerService).
Вызов inject(LoggerService) запрашивает сервис LoggerService.
Если LoggerService еще не был создан ранее, Angular создает его экземпляр и кэширует в Root Injector.
  Шаг 3. Завершение создания и кэширование (Сворачивание стека)
После того как LoggerService разрешен, процесс возвращается обратно по цепочке вызовов, завершая инстанцирование и кэширование каждого класса:
Завершение D:
Класс D получает экземпляр LoggerService в поле logger.
Создание D завершено.
Root Injector сохраняет (кэширует) созданный экземпляр D в своей внутренней карте (Map), чтобы повторные вызовы inject(D) возвращали этот же объект.
Экземпляр D передается наверх в сервис C.
Завершение C:
Класс C получает экземпляр D в поле d.
Создание C завершено.
Root Injector кэширует экземпляр C.
Экземпляр C передается наверх в сервис B.
Завершение B:
Класс B получает экземпляр C в поле c.
Создание B завершено.
Root Injector кэширует экземпляр B.
Экземпляр B передается наверх в сервис A.
Завершение A:
Класс A получает экземпляр B в поле b.
Создание A полностью завершено.
Root Injector кэширует экземпляр A.
  Итоговый результат
По завершении первоначального вызова inject(A) в Root Injector окажутся закэшированы все 5 экземпляров (LoggerService, D, C, B, A). При любых последующих вызовах inject(A), inject(B) и т.д. Angular сразу вернет готовые ссылки из кэша за O(1) без повторного вызова конструкторов.


Задача №14:
1. Сколько объектов существует в памяти до вызова inject?
  0 объектов сервисов. Почему?
В Angular DI-контейнер работает по принципу ленивой инициализации (Lazy Initialization). Объявление @Injectable({ providedIn: 'root' }) лишь регистрирует инструкцию для Angular (рецепт того, как создавать сервис при необходимости). Ни один сервис не будет создан в памяти до тех пор, пока его явно не запросят через inject() или через параметр конструктора.

2. Сколько объектов появится после вызова inject(UserService)?
  Появится 3 новых объекта: LoggerService, ApiService и UserService. Почему?
При вызове inject(UserService) Angular разрешает цепочку зависимостей по схеме «снизу вверх» (глубокий рекурсивный поиск / каскадное создание):
UserService: Angular пытается создать его экземпляр, но видит, что сервису требуется ApiService. Создание UserService приостанавливается.
ApiService: Angular начинает создавать ApiService, но видит, что ему требуется LoggerService. Создание ApiService приостанавливается.
LoggerService: Сервис не имеет внешних зависимостей. Angular создаёт его экземпляр (1-й объект) и сохраняет в кэш Root Injector.
Завершение ApiService: Получив готовую ссылку на LoggerService, Angular полностью создаёт ApiService (2-й объект) и кэширует его.
Завершение UserService: Получив готовую ссылку на ApiService, Angular создаёт UserService (3-й объект) и кэширует его.
Все 3 созданных объекта сохраняются в реестре Root Injector для последующего повторного использования.


Задача №15: Вот оптимальный способ регистрации для каждого из 13 сервисов с объяснением архитектурного решения, основанного на механизмах Dependency Injection (DI) в Angular:

1. ApiService
  Решение: providedIn: 'root'
Почему: HTTP-клиент нужен повсюду. Это классический Singleton, который должен жить от старта до завершения работы приложения. Нет смысла создавать его копии.

2. AuthService
  Решение: providedIn: 'root'
Почему: Состояние авторизации (текущий пользователь, токен) — это глобальное состояние. Запрашивать его могут header (для показа аватарки), guards (для защиты роутов), interceptors (для добавления токена). Должен быть строго один экземпляр.

3. CartService
  Решение: providedIn: 'root'
Почему: Корзина не должна очищаться при переходе со страницы товара на страницу оформления заказа. Состояние должно сохраняться на протяжении всей сессии пользователя.

4. ProductFilterService
  Решение: providers компонента (на уровне PhonesComponent и LaptopsComponent)
Почему: Регистрация в providers компонента привязывает жизненный цикл сервиса к жизненному циклу компонента. Как только пользователь уходит со страницы "Телефоны", компонент уничтожается, и инжектор уничтожает экземпляр ProductFilterService вместе с выбранными фильтрами. При заходе на "Ноутбуки" создается новый, чистый экземпляр.

5. NotificationService
  Решение: providedIn: 'root'
Почему: Уведомления могут вызываться откуда угодно (из перехватчиков ошибок, компонентов, других сервисов). Контейнер для тостов (например, в AppComponent) должен слушать единый глобальный поток событий.

6. ThemeService
  Решение: providedIn: 'root'
Почему: Глобальная настройка приложения. Переключение темы в одном месте должно мгновенно отразиться на всех остальных частях приложения.

7. DashboardStatisticsService
  Решение: providers компонента (на уровне DashboardComponent) ИЛИ providers роутинга (в маршруте /dashboard).
Почему: Строго ограниченная область видимости. Сервис инициализируется при заходе на дашборд и уничтожается сборщиком мусора при уходе (срабатывает хук ngOnDestroy сервиса, где можно отменить HTTP-запросы). Это экономит оперативную память.

8. UserTableStateService
  Решение: providers компонента (на уровне родительского UsersPageComponent)
Почему: Данные (пагинация, сортировка) должны шариться между дочерними компонентами этой страницы (таблица, пагинатор, панель поиска), но при этом состояние должно сбрасываться при уходе со страницы. Локальный провайдер родительского компонента идеально подходит: все дети получат один экземпляр, который умрет вместе со страницей.

9. ModalService
  Решение: providedIn: 'root'
Почему: Управление наложением (overlay) и состоянием окон требует единой точки истины на все приложение, иначе разные компоненты могут наплодить независимые стейты модалок.

10. LoggerService
  Решение: useFactory
Почему: Требуется условная логика при инициализации. Фабрика проверит environment.production: если true — вернет экземпляр класса ServerLogger, если false — экземпляр класса ConsoleLogger. (Часто комбинируется с providedIn: 'root').

11. AppConfig
  Решение: InjectionToken + useValue
Почему: Конфигурация — это обычно простой объект (JSON/Interface), а не инстанцируемый класс (Class). Angular DI не может использовать TypeScript-интерфейсы как токены (они исчезают после компиляции). Поэтому мы создаем new InjectionToken('AppConfig') и передаем сам объект конфига через useValue.

12. CurrencyFormatter
  Решение: InjectionToken + useValue (если это просто строка формата, например 'USD') ИЛИ providedIn: 'root' (если это класс с методами форматирования).
Почему: Если речь идет о сохранении выбранного "формата" (строка/объект), то применяется связка Token + Value. Это позволяет легко подменять формат валюты для разных рынков при сборке или запуске.

13. AnalyticsService
  Решение: useFactory
Почему: Зависит от условия (включена ли аналитика). В фабрике мы проверяем конфиг: если аналитика отключена, фабрика может вернуть null (или заглушку MockAnalyticsService, у которой методы пустые). Если включена — возвращает new GoogleAnalyticsService(). Это избавляет приложение от выполнения лишнего кода.
