Архитектурный рефакторинг Angular-приложения

1. Выбранные архитектурные подходы и паттерны

В рамках рефакторинга были выбраны следующие подходы:
  Feature-Based Architecture — основа структуры приложения.
  Core / Shared — разделение глобальных сервисов и переиспользуемых компонентов.
  Facade Pattern — сервисы-фасады для сокрытия работы с API и состоянием от компонентов.
  Component-Based Design (CBD) — разделение UI на самостоятельные компоненты.
  RxJS — управление асинхронными операциями и состоянием.
  OOD (Object-Oriented Design) — разделение ответственности между классами и сервисами.

Основным архитектурным принципом выбран Feature-Based подход в сочетании с Core/Shared.


2. Почему выбран этот подход

До рефакторинга структура проекта была преимущественно плоской: компоненты, сервисы, интерфейсы, enum, pipes и directives находились в общих папках.

Например, разные части приложения использовали одни и те же глобальные папки:
services/
interfaces/
enums/
components/

При увеличении проекта такая структура становится менее удобной:
сложно определить, к какой функциональной области относится файл;
одна feature может зависеть от большого количества разрозненных файлов;
сложнее поддерживать и расширять приложение;
повышается связность между различными частями приложения;
структура проекта плохо отражает бизнес-функциональность.

Поэтому структура была изменена на Feature-Based.

Теперь основные функциональные области приложения изолированы:
features/
├── auth/
├── home/
├── posts/
└── users/

Каждая feature содержит связанные с ней модели, страницы, UI-компоненты, сервисы и другие элементы.
Это позволяет при дальнейшем развитии приложения работать преимущественно внутри конкретной feature, не просматривая множество глобальных папок.


3. Core и Shared

Для кода, который не относится к конкретной бизнес-фиче, использовано разделение Core / Shared.

Core

Core содержит глобальную инфраструктуру приложения:
core/
├── enums/
├── interceptors/
├── models/
├── services/
└── tokens/

В него вынесены:
глобальные сервисы;
interceptors;
application configuration;
tokens;
глобальные модели и enum.

Например, ThemeService, LoaderService, MessageService, LocalStorageService относятся ко всему приложению, поэтому находятся в Core.

Shared

Shared содержит переиспользуемые элементы:
shared/
├── components/
├── directives/
├── enums/
├── models/
└── pipes/

Здесь находятся общие UI-компоненты, directives и pipes, которые не принадлежат конкретной бизнес-фиче.

Такое разделение позволяет отличать глобальную инфраструктуру приложения от переиспользуемого UI и вспомогательного кода.


4. Facade Pattern и разделение UI и логики

Для работы компонентов с данными используются сервисы, которые выступают в роли фасадов.

Например:
features/posts/data-access/
├── post-api.service.ts
└── post.service.ts

PostApiService отвечает непосредственно за взаимодействие с API.
PostService скрывает от компонентов детали работы с данными и состоянием постов.
Аналогичный подход используется для пользователей и авторизации.
В результате компоненты не должны самостоятельно содержать всю логику работы с API, хранения состояния и обработки данных.
Это уменьшает связность компонентов и делает код проще для поддержки и тестирования.


5. Component-Based Design

UI разделён на самостоятельные компоненты.

Например, внутри features выделены страницы и UI-компоненты:
posts/
├── pages/
└── ui/

users/
├── pages/
└── ui/

А переиспользуемые элементы приложения находятся в:
shared/components/

Такое разделение позволяет:
уменьшить размер отдельных компонентов;
повторно использовать UI;
отделить страницы от специализированных UI-компонентов;
упростить дальнейшее развитие приложения.


6. Управление состоянием — RxJS

В проекте используется RxJS.

Это решение выбрано потому, что приложение уже активно работает с Observable и HTTP API.

Например, состояние данных в сервисах может представляться через BehaviorSubject, а компоненты получают данные через Observable.

Преимущество такого подхода для текущего проекта — отсутствие необходимости вводить дополнительную библиотеку управления состоянием.

RxJS хорошо подходит для:
HTTP-запросов;
асинхронных операций;
потоков данных;
реактивного взаимодействия между сервисами и компонентами.


7. Почему не Redux

Redux является хорошим решением для приложений со сложным глобальным состоянием, большим количеством взаимосвязанных действий и необходимостью централизованного predictable state management.

Однако для текущего приложения Redux был бы избыточен.

Основное состояние приложения относительно небольшое, а уже существующий RxJS позволяет решить необходимые задачи без дополнительного boilerplate и отдельной инфраструктуры actions/reducers/selectors.

Поэтому использование Redux увеличило бы сложность проекта без существенной практической пользы.


8. Почему не Signals

Signals являются современным механизмом Angular для реактивного состояния и хорошо подходят для многих сценариев.

Однако текущий проект уже использует RxJS для работы с Observable и HTTP.

Переход на Signals именно в рамках архитектурного рефакторинга потребовал бы дополнительной миграции существующей логики, но не дал бы существенного архитектурного преимущества для текущего масштаба приложения.

Поэтому было принято решение сохранить единый подход на основе RxJS.


9. Почему не Layered Architecture

Layered Architecture хорошо подходит для строгого разделения технических слоёв, например:
presentation/
application/
domain/
infrastructure/

Однако для данного приложения такой подход мог бы снова привести к ситуации, когда код одной функциональной области оказывается распределён по нескольким глобальным папкам.

Feature-Based структура лучше отражает функциональность приложения:
features/
├── auth/
├── posts/
└── users/

Поэтому для данного проекта Feature-Based подход является более удобным.


10. Почему не DDD

DDD полезен для систем со сложной предметной областью, большим количеством бизнес-правил, bounded contexts и богатой доменной моделью.

Текущее приложение является учебным CRUD-приложением с авторизацией, пользователями и постами.

Полноценное применение DDD здесь создало бы дополнительную сложность и большое количество абстракций, которые не дают существенной пользы на текущем уровне проекта.

Поэтому был выбран более лёгкий OOD-подход, достаточный для текущей сложности приложения.


11. Почему не TDD

TDD является методологией разработки, ориентированной на разработку через тесты.

Основная задача текущего этапа — архитектурная реорганизация существующего приложения.

Поэтому TDD не выбран в качестве основной методологии данного рефакторинга. В рамках этой задачи приоритетом было разделение ответственности и построение масштабируемой структуры проекта.

13. Результат

В результате рефакторинга:
устранена плоская структура проекта;
функциональность разделена по features;
глобальная инфраструктура вынесена в Core;
переиспользуемые элементы вынесены в Shared;
UI и работа с данными разделены;
сервисы используются как фасады между компонентами и data-access;
сохранён существующий RxJS-подход;
относительные импорты обновлены после перемещения файлов;
приложение успешно проходит TypeScript compilation;
production build успешно завершается;
основные маршруты и функциональность приложения проверены после рефакторинга.

Таким образом, новая структура лучше отражает ответственность частей приложения и создаёт основу для дальнейшего масштабирования без возвращения к плоской структуре.
